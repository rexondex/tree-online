# 온라인 생활형 3D RPG 기획 및 기술 설계

> 상태: 로컬 멀티플레이 프로토타입 구현 중. 실제 실행 방법과 구현 범위는 15절을 참고한다. 나머지 설계와 성능 수치는 목표 또는 제안이다.

## 1. 프로젝트 목표

마비노기 모바일에서 느낄 수 있는 공동체, 모험, 전투와 생활의 조화를 참고하여, 독자적인 세계관과 자산으로 제작하는 경량 3D 온라인 RPG. 궁극적으로 지속적으로 확장 가능한 대규모 멀티플레이 게임을 지향한다. 초기는 작은 마을과 필드에서 여러 사람이 같은 세계를 공유하고 전투·채집·제작·성장을 경험하는 데 집중한다.

- PC용 Electron 실행 파일 한 인스턴스가 한 사용자의 게임 화면과 세션을 담당한다. 한 컴퓨터에서 실행 파일 두 개를 실행하여 서로 다른 계정으로 같은 서버에 접속할 수 있어야 한다.
- 동일한 서버 프로그램을 개발자의 로컬과 향후 원격 호스트에서 실행한다. 클라이언트는 설정된 서버 주소로 접속하며 원격 배포를 위해 게임 규칙을 새로 작성하지 않는다.
- 첫 성능 목표는 **동일 서버의 동시 접속 20~100명**이다. 특히 같은 지역에 모인 경우를 별도로 측정한다. 목표치이며 아직 보장이나 검증 결과가 아니다.
- 로그인, 캐릭터, 영구 저장, 이동, 전투, 경험치와 레벨, HP·MP, 아이템, 인벤토리, 장비, 채집, 제작, 채팅을 단계적으로 구현한다.
- 최초 목표는 화려한 외형보다 통신, 서버 권한, 데이터 정합성, 실행 및 배포 가능성을 검증하는 것이다.

## 2. 라이선스 정책과 기술 선택

목표는 자체 게임 엔진과 게임을 개발하고 수정·배포·상용 서비스할 수 있는 기술을 사용하는 것이다. MIT만 고집하지 않고, 상용 이용과 수정·배포가 가능한 허용적 오픈소스 라이선스를 채택한다. 사용자 수나 매출에 따른 엔진 사용료, 로열티, 기능 제한, 별도의 상용 라이선스 계약을 요구하는 기술에는 의존하지 않는 것을 원칙으로 한다. 호스팅·인프라·플랫폼 비용은 별개다.

| 구성 | 선택 및 역할 | 라이선스와 확인 사항 |
| --- | --- | --- |
| Electron | PC 실행 파일과 앱 셸 | 프로젝트 MIT. Chromium·Node.js 등 포함 구성요소와 바이너리의 제3자 고지를 별도 검토한다. |
| Vite | 클라이언트 개발 및 빌드 | 코어 MIT. 배포 패키지의 BSD·ISC 등 포함 라이선스도 확인한다. |
| TypeScript | 클라이언트·서버 및 엔진 개발 언어와 도구 | 공식 컴파일러 Apache-2.0. 상업적 사용·수정·배포가 가능하며 해당 조건을 준수한다. |
| Node.js | 서버 실행 환경 | 프로젝트 MIT. 포함된 외부 구성요소의 라이선스와 고지를 검토한다. |
| Three.js | 자체 엔진의 3D 렌더링 기반 | MIT. 엔진의 월드, 카메라, 입력, 자원, 게임 로직은 프로젝트에서 구성한다. |
| Colyseus | 실시간 연결·방·상태 동기화 후보 | 핵심 프로젝트 MIT. 실제 채택할 패키지·버전·간접 의존성을 검증한다. 사용 여부는 프로토타입에서 결정한다. |
| PostgreSQL | 계정·캐릭터·인벤토리 영구 저장 후보 | PostgreSQL License. 상업적 사용을 허용하는 허용적 라이선스다. 드라이버와 배포 구성은 별도로 검토한다. |

MIT, BSD, ISC, Apache-2.0, PostgreSQL License와 같은 허용적 라이선스를 우선 검토한다. Apache-2.0은 해당 시 라이선스 사본, 변경 표시 및 NOTICE 등 조건을 확인한다. MIT/BSD 등도 요구되는 저작권 표시와 라이선스 문구를 보존한다. GPL·AGPL 등 강한 카피레프트, SSPL, 비상업 전용, 소스 공개 조건이 자체 엔진의 배포 방침과 충돌하는 라이선스나 별도 계약이 필요한 기술은 기본적으로 채택하지 않는다. LGPL 등 파일·라이브러리 단위의 의무가 있는 구성요소는 일괄적으로 무시하거나 승인하지 않고 실제 배포 형태와 의무를 검토한다. Electron 배포물에 포함된 구성요소도 이 절차에 포함된다.

직접 작성한 엔진과 게임 코드의 권리는 작성자와 기여 계약에 따라 관리하며, 자체 코드를 공개할지는 프로젝트의 별도 결정이다. 제3자 코드를 수정하거나 포함하면 그 코드의 권리가 프로젝트에 이전되는 것은 아니며, 각 라이선스의 고지·배포 조건을 계속 지켜야 한다. 게임 엔진 자체의 라이선스는 아직 정하지 않았다.

오픈소스 라이선스는 동시 접속 인원에 따른 로열티가 없더라도 성능·운영비, 상표, 특허, 자산 권리, 플랫폼·클라우드 약관 및 법적 의무까지 없애지는 않는다. 실제 사용 버전과 전체 의존성 및 최종 배포물을 감사하며, 특정 구성의 법적 무위험이나 성능을 보장하지 않는다.

참고: [TypeScript](https://github.com/microsoft/TypeScript), [Vite 라이선스](https://github.com/vitejs/vite/blob/main/packages/vite/LICENSE.md), [Electron 소개](https://github.com/electron/electron/blob/main/docs/why-electron.md), [Node.js](https://github.com/nodejs/node), [Three.js 라이선스](https://threejs.org/license/), [Colyseus](https://github.com/colyseus/colyseus), [PostgreSQL 라이선스](https://www.postgresql.org/about/licence/).
## 3. IP 및 콘텐츠 원칙

참고하는 것은 생활형 온라인 RPG의 일반적인 게임 경험이다. 게임명, 세계관, 캐릭터, 지명, 대사, 지도, UI 표현, 모델, 애니메이션, 음악과 사운드는 독자 제작하거나 해당 사용 범위의 명시적 허가를 받는다. 마비노기의 게임 파일 추출이나 공식 서버 연결은 하지 않는다. 상용 서비스 전 자산 및 구체적인 유사성에 대한 권리 검토가 필요하다.

모델·텍스처·폰트·효과음 등도 코드와 별개로 출처, 제작자, 라이선스, 상업적 이용·수정·재배포 허용 범위와 표시 의무를 기록한다. 자산의 라이선스와 직접 제작 자산의 권리 귀속을 개별적으로 확인한다. 출처 불명 자산은 사용하지 않는다.

## 4. 전체 구성

```text
Electron 클라이언트 A ─┐
                       ├─ HTTPS/WSS ─ 인증/API ─ 세션 관리
Electron 클라이언트 B ─┘                  │
                                        └─ 월드/지역 서버 ─ 영구 저장소
                                             │
                                      게임 규칙·상태·검증
```

- **클라이언트:** 로그인 화면, 3D 렌더링, 카메라, 입력, HUD, 인벤토리와 채팅. 플레이어의 입력을 서버에 전송하고 서버 결과를 화면에 표현한다.
- **인증/API:** 계정 생성, 로그인, 세션 발급·폐기, 캐릭터 선택, 상태 및 버전 확인. 초기에는 게임 서버와 한 프로세스로 구성할 수 있다.
- **월드 서버:** 연결 관리, 고정 주기 시뮬레이션, 지역, 이동·전투·보상 등 게임 규칙의 최종 권한을 가진다.
- **영구 저장소:** 계정, 캐릭터, 능력치, 위치, 아이템, 장비, 제작 결과를 저장한다. PostgreSQL을 후보로 하며 실제 버전과 드라이버의 라이선스를 검증한다.
- **공유 계약:** 클라이언트와 서버가 사용하는 메시지 스키마, 식별자, 프로토콜 버전 및 정적 데이터 정의. 클라이언트에 공유한 계산 코드를 신뢰의 근거로 삼지 않는다.

초기에는 단일 프로세스와 단일 지역으로 개발하고 경계를 분명히 한다. 이후 지역별 프로세스, 인스턴스 던전, 서버 간 전달 및 운영 도구를 필요에 따라 분리한다. 분리만으로 대규모 수용이 보장되지는 않는다.

## 5. 클라이언트 설계

- Electron main 프로세스는 창과 앱 수명 주기만 관리한다. preload는 필요한 최소 기능만 노출한다. renderer는 Vite 기반 화면과 3D 장면을 담당한다. 각 구성은 실제 채택 버전과 배포물의 라이선스를 검증한 뒤 도입한다.
- `contextIsolation`과 샌드박스를 사용하고 renderer에서 Node 통합을 끈다. 외부 페이지 이동, 임의 URL 열기와 IPC는 제한하고 검증한다. 비밀번호나 토큰을 로그에 남기지 않는다.
- 로그인 → 서버 선택 또는 주소 설정 → 캐릭터 선택·생성 → 월드 입장 순서. 끊김, 버전 불일치, 서버 점검을 화면에 알린다.
- 서버 주소는 개발용 로컬 주소와 배포용 주소를 설정으로 구분한다. 출시 클라이언트에 비밀키를 넣지 않는다. 프로덕션은 인증서 검증이 되는 HTTPS/WSS를 사용한다.
- 클라이언트의 이동 예측과 다른 플레이어 보간은 체감 지연을 줄이기 위한 표현이다. 서버의 위치와 결과에 맞춰 보정한다.
- 기본은 키보드/마우스 조작의 PC 3D 클라이언트다. 모바일 실행은 별도 목표로 다루며 Electron만으로 모바일 지원을 가정하지 않는다.

## 6. 서버와 네트워크

- 서버가 시간, 이동 가능 거리, 충돌, 공격 거리·속도·재사용 대기시간, 피해, 자원 소모와 보상을 검증한다. 클라이언트는 최종 좌표나 보상 수치를 신뢰할 수 있는 사실로 제출하지 않는다.
- 실시간 연결은 WebSocket을 후보로 한다. 클라이언트 입력에는 순번을 두고, 서버는 고정 tick에서 처리하며 상태 스냅샷에는 tick/순번을 포함한다. 초기 tick 및 송신 주기는 부하 측정 후 결정한다.
- 메시지 크기, 형식, 속도와 인증 상태를 검증한다. 스팸 및 비정상 입력 제한, 접속 종료, 재접속 정책을 둔다. 버전 불일치는 명시적으로 거부한다.
- 관심 영역(AOI)으로 가까운 객체 위주로 전송하고, 변경분 전송 및 전송 빈도를 측정해 최적화한다. 100명이 한 지점에 모이면 전송량이 급증하므로 별도 부하 시나리오로 검증한다.
- 연결 끊김 시 캐릭터의 월드 이탈, 저장, 세션 만료와 재접속 처리를 정의한다. 중복 로그인은 초기에는 기존 세션 종료 또는 신규 세션 거부 중 하나를 구현 시 명시하고 일관되게 적용한다.
- 거래·제작·보상은 서버가 유일한 작업 ID와 원자적 저장을 사용해 중복 지급을 방지한다. 저장 실패 시 성공을 클라이언트에 확정하지 않는다.

## 7. 계정, 데이터와 보안

- 최소 계정: 고유 ID, 로그인 식별자, 안전한 비밀번호 해시, 생성·상태 정보. 캐릭터: 소유 계정, 이름, 지역·위치, 레벨·경험치, HP·MP, 인벤토리·장비 및 생활 진행도.
- 비밀번호는 평문 또는 단순 해시로 저장하지 않는다. 검증된 비밀번호 해싱 구현과 무작위 salt를 사용하며, 해당 구현과 의존성의 라이선스를 채택 전에 검사한다. 로그인 요청 제한, 세션 만료 및 폐기를 구현한다.
- 저장소의 트랜잭션, 고유 제약과 마이그레이션을 사용하고 백업 복구를 시험한다. 서버 재시작 후 캐릭터와 획득 아이템이 유지되어야 한다. 게임 데이터를 클라이언트 로컬 파일에만 의존하지 않는다.
- 테스트 계정·비밀값은 환경 설정으로 분리한다. 운영 환경에는 TLS, 접근 제어, 보안 업데이트, 개인정보 처리 방침 및 운영상 필요한 관리 절차가 필요하다.

## 8. 게임 시스템

1. **캐릭터:** 계정에 귀속된 캐릭터의 생성과 선택. 초기에는 기본 외형 1종.
2. **월드:** 마을 1곳과 작은 필드 1곳, 충돌과 리스폰 지점. 지역 이동은 서버가 승인한다.
3. **이동:** 키 입력을 서버에 보내며 속도와 이동 가능 위치를 서버가 검증한다.
4. **전투:** 몬스터 1종, 기본 공격, 타격 범위와 쿨다운. 서버가 몬스터 AI, HP, 사망과 보상을 처리한다.
5. **성장:** 서버가 경험치를 지급하고 레벨 및 능력치 변화를 계산한다. 성장 곡선과 상한은 플레이 테스트로 조정한다.
6. **HP와 MP:** 서버가 피해, 회복, 마나 소모와 재생을 계산한다. 초기 스킬 1종으로 MP 사용을 검증한다.
7. **인벤토리와 장비:** 아이템 정의와 개별 보유량, 슬롯, 장착 조건 및 능력치 반영. 이동·장착 요청은 소유권과 상태를 확인한다.
8. **채집과 제작:** 채집 대상과 재생 시간, 재료 획득, 제작법 1종. 서버가 거리와 재료를 검증하고 재료 차감 및 결과 지급을 한 트랜잭션으로 처리한다.
9. **소통:** 같은 지역 채팅, 기본적인 길이·속도 제한. 신고와 관리 기능은 공개 서비스 전에 보완한다.
10. **장기 확장:** 파티, 던전, 퀘스트, 낚시, 다양한 직업·장비와 경제 시스템. 범위와 일정은 프로토타입 검증 후 정한다.

## 9. 성능 목표 및 검증

20~100명은 우선 단일 서버에서의 동시 접속 목표이며, 전체 계정 수나 수천 명의 동시 접속을 의미하지 않는다. 같은 지역 100명도 목표 시나리오에 포함하되 하드웨어와 네트워크 조건에 따라 결과가 달라진다.

- 20명과 100명 각각에 대해 접속 유지, 이동, 전투, 채팅, 채집 및 저장이 섞인 부하를 재현한다. 분산 배치와 한 지점 밀집을 각각 시험한다.
- 측정 항목: 서버 tick 지연과 누락, CPU·메모리, 초당 송수신량, 연결 수, 저장 지연 및 오류, 클라이언트 FPS, 이동 지연·보정, 재접속 성공률.
- 테스트 환경, 서버 사양, 인원, 봇 행동, 측정 시간, 중앙값과 p95/p99, 오류율을 함께 기록한다. 목표 허용치는 실제 게임 조작 감각과 시제품 결과를 바탕으로 확정한다.
- 자동 부하 클라이언트만으로 렌더링 성능을 판단하지 않는다. 최소 2개의 실제 Electron 클라이언트로 기능을 확인하고 대표 사양에서 별도로 렌더링을 측정한다.

## 10. 로컬 실행 및 검증 계획

실제 실행 명령은 15절을 참고한다. 전체 목표 검증 절차는 다음과 같다.

1. 로컬 저장소와 게임 서버를 실행한다. 개발용 설정에서 루프백 주소와 포트를 사용한다.
2. Electron 클라이언트 인스턴스 두 개를 별도 프로세스로 실행한다. 동일 사용자 데이터 디렉터리 잠금이나 세션 공유 때문에 두 번째 인스턴스가 막히지 않도록 개발 실행 방식을 설계한다.
3. 서로 다른 계정으로 가입·로그인하고 각 캐릭터를 같은 지역에 입장시킨다.
4. 서로의 이동과 채팅, 몬스터 전투 결과 및 채집 상태가 양쪽에 일관되게 표시되는지 확인한다.
5. 아이템 제작과 장착 후 양쪽 클라이언트 및 서버를 종료·재시작하고 계정과 캐릭터 데이터가 유지되는지 확인한다.
6. 강제 연결 종료, 재접속, 중복 로그인, 잘못된 입력 및 저장 실패를 시험한다.

동일 PC의 `127.0.0.1`은 해당 PC 자신을 가리킨다. 다른 PC에서 접속하려면 서버의 LAN 주소, 서버 바인딩 및 방화벽 설정이 필요하다. 개발 환경을 외부 인터넷에 무분별하게 노출하지 않는다.

## 11. 원격 배포 계획

- 로컬과 동일한 서버 코드를 환경 변수로 주소, 포트, 저장소, 인증 및 로그 설정만 바꾸어 실행한다. 원격 서버에서는 클라이언트 주소에 접근 가능한 도메인을 설정한다.
- AWS 등의 가상 서버는 후보일 뿐 필수 서비스가 아니다. 운영체제와 이미지, 런타임, 관리형 서비스 및 그 약관·비용은 별도로 검토한다. 클라우드 서비스 자체를 MIT 소프트웨어로 간주하지 않는다.
- 방화벽은 필요한 포트만 개방하고 외부에 HTTPS/WSS를 제공한다. 저장소는 공개망에서 직접 접근하지 못하도록 한다. 인증서 갱신, 비밀값 관리, 백업·복원, 모니터링, 알림, 장애 복구와 업데이트 절차를 준비한다.
- 배포 실행 파일은 빌드 버전, 프로토콜 버전, 서버 주소, 제3자 라이선스 고지 및 업데이트 정책을 포함한다. 코드 서명, 배포 플랫폼 및 인증서에는 별도 조건과 비용이 발생할 수 있다.
- 단일 서버를 넘어설 때 지역 분할, 접속 라우팅, 프로세스 간 메시지, 데이터 소유권 및 장애 복구를 설계하고 실측한다. 자동 확장이나 무제한 동시 접속을 전제하지 않는다.

## 13. 구현 순서 및 완료 기준

- **0. 기반 선정:** 상용 이용·수정·배포 조건을 확인하고 선택한 구성요소의 정확한 버전 및 라이선스를 감사한다.
- **1. 연결 기반:** 서버 실행, 두 클라이언트 접속, 기본 3D 공간과 서버 권한 이동. 양쪽에서 서로를 확인한다.
- **2. 계정과 저장:** 가입·로그인·캐릭터 선택 및 재시작 후 복원. 비밀번호 해시, 세션, 저장 실패를 검증한다.
- **3. 게임 루프:** 몬스터, 전투, 경험치·레벨, HP·MP, 인벤토리와 장비. 두 클라이언트에서 같은 결과를 확인한다.
- **4. 생활:** 채집과 제작 및 원자적 영구 저장을 검증한다.
- **5. 성능·배포:** 20명부터 100명까지 부하를 단계적으로 측정하고 병목을 해결한다. 원격 서버와 패키지 클라이언트로 접속 검증한다.

각 단계는 동작과 검증을 완료한 뒤 다음 단계로 진행한다. 전투·경제의 수치와 콘텐츠 범위는 검증에 따라 수정할 수 있다.

## 14. 라이선스 관리 절차

1. 의존성 추가 전 직접·간접 패키지, 번들 런타임 및 빌드 도구의 버전, 원문 라이선스와 포함 파일을 조사한다. SPDX 표기만으로 결론 내리지 않는다.
2. 상용 이용, 수정 및 배포 권한과 고지·소스 공개·특허 등 조건을 검토한다. 정책에 맞지 않거나 불명확한 항목은 보류하고 대체재를 찾는다.
3. 잠금 파일과 소프트웨어 구성 목록을 유지하고 업데이트 때 재검사한다. 배포물에 요구되는 원문·저작권·고지를 포함한다.
4. 자산은 별도 목록에 출처, 사용 허락 및 변경 이력을 기록한다. 서비스 약관 및 콘텐츠 권리는 오픈소스 라이선스 검사와 별도로 확인한다.
5. 릴리스마다 실제 설치 파일과 서버 배포물까지 감사한다. 라이선스 준수와 성능은 자동으로 영구 보장되는 속성이 아니다.


## 15. 현재 구현 및 로컬 실행

현재 저장소에는 개발용 프로토타입이 구현되어 있다. 계정당 캐릭터 하나, 3D 이동, 전투·성장·채집·제작·장비의 기초 코드와 서버 상태 API가 있다. 지역 채팅의 기초 코드가 추가되었으며 관리자 UI와 설치 파일 다운로드 페이지는 아직 구현되지 않았다. 실제 검증 여부와 미완료 항목은 17절과 개발 요구사항 문서를 참고한다.

### 준비 및 실행

Node.js와 npm 설치 후 프로젝트 폴더에서 다음을 실행한다. 일반적으로 `npm`을 사용하면 된다. Windows PowerShell에서 스크립트 실행 정책 때문에 `npm.ps1`이 차단될 때만 `npm.cmd`를 대신 사용한다.

```powershell
npm install
npm run server
```

별도 터미널에서 클라이언트를 빌드하고 두 번 실행한다.

```powershell
npm run build
npm run client
```

`npm run client`를 다른 터미널에서 한 번 더 실행한다. 두 창에서 각각 서로 다른 영문·숫자·밑줄 아이디와 8자 이상의 비밀번호로 회원가입한 후 로그인한다. WASD 또는 방향키로 움직이면 상대 캐릭터가 보인다. 서버 상태 및 안내 페이지는 http://127.0.0.1:3000 이다. `npm run typecheck`로 타입 검사를 실행한다. `npm run package`는 Windows용 폴더형 빌드를 생성하는 명령이며 배포용 서명과 설치 프로그램은 아직 구성하지 않았다.

### 데이터베이스와 설정

기본은 PostgreSQL 엔진 기반 PGlite이며 데이터는 `.data/postgres`에 영구 저장된다. 별도의 PostgreSQL 서버나 Docker가 필요하지 않다. 실제 PostgreSQL 서버로 전환할 때 `.env.example`을 `.env`로 복사하고 `DATABASE_URL=postgresql://사용자:비밀번호@호스트:포트/DB명`을 설정한다. 동일한 SQL과 저장소 인터페이스를 사용하나 기존 PGlite 데이터가 자동 이전되지는 않는다. 원격 PostgreSQL 연결 및 데이터 이전은 아직 실환경에서 검증하지 않았다. `.env`와 데이터 폴더는 Git에 포함하지 않는다.

`PORT` 기본값은 3000이고 `HOST` 기본값은 127.0.0.1이다. LAN에서 시험하려면 `HOST`와 방화벽 및 접속 주소를 별도 설정한다. `ADMIN_TOKEN`을 설정하면 `GET /api/admin/stats`를 Bearer 토큰으로 조회할 수 있다. 토큰을 설정하지 않으면 API는 비활성화된다. 이 서버는 로컬 개발용으로, HTTPS/WSS 종료, 로그인 요청 제한, 운영용 세션 관리 및 보안 강화가 아직 없어 인터넷에 그대로 공개하면 안 된다.

### 검증 현황

타입 검사와 클라이언트 빌드, 서버에서 서로 다른 두 테스트 계정의 인증과 WebSocket 공유 상태 수신을 확인했다. 20~100명 부하, 패키징 결과, 원격 DB, 실제 두 Electron 창의 시각적 동작은 별도 검증이 필요하다. npm 의존성의 실제 버전·간접 의존성 및 Electron 배포물의 라이선스 감사와 고지 파일 구성은 릴리스 전 필수 작업이다.



## 16. 개발 요구사항과 예정 폴더

사용자 관점의 전체 요구사항과 검증 현황은 단일 문서 [develop/EVELOPMENT.md](develop/EVELOPMENT.md)에서 관리한다. 새로운 요구사항도 이 문서에 추가하고 코드상 구현을 완료하면 체크한다. 체크와 실제 테스트 결과는 구분해 기록한다.

`client/engine`, `client/game`, `client/network`, `client/ui`, `server/auth`, `server/network`, `server/world`, `server/game`, `server/persistence`, `server/admin`, `shared`, `tools`, `tests`는 향후 역할별 코드 분리를 위한 자리다. `public/assets` 아래에는 캐릭터 모델·애니메이션, 장비, 이펙트, 월드, 오디오, UI와 자산 목록용 경로를 준비했다. 빈 경로는 `.gitkeep`으로 유지한다. 현재 실행 코드는 여전히 `client/main.ts`, `server/index.ts`, `electron/main.cjs`에 있으며 폴더 생성 자체가 모듈 로더나 자산 등록 기능을 제공하지 않는다.

나중에 자산을 추가할 때는 식별자와 파일 경로, 버전, 출처와 라이선스를 관리하고 캐릭터·장비·스킬 데이터에서 참조하는 방식을 구현한다. 서버는 게임 규칙과 유효한 장비·기술을 관리하고 클라이언트는 그 결과에 맞는 시각 자산을 표현한다. 정확한 등록 포맷과 배포·호환성 검증은 해당 기능 구현 시 확정한다.

## 17. 현재 진행 상태

[개발 요구사항](develop/EVELOPMENT.md)의 체크는 코드상 구현을 의미하며 실제 플레이 검증의 통과 표시가 아니다. 현재 계정당 캐릭터 하나의 생성·선택, 이름 표시, 상태, 공격·마법·몬스터·성장, 채집·제작·장비와 지역 채팅의 기초 코드가 추가되었다. 재료는 E, 공격은 1, 마법은 2, 제작은 C, 장비 착용은 F로 조작한다. 기존 계정은 최초 로그인 시 캐릭터 이름을 새로 지정한다. 이전 프로토타입의 위치는 새 캐릭터에 자동 이전되지 않는다.

코드 변경 후 `npm run build`로 클라이언트를 다시 빌드하고 서버를 재시작해야 한다. 저장 실패 대응, 자산 등록, 배포 패키지 검증, 다중 사용자 실플레이 및 20~100명 부하 등은 미완료다. 이 버전은 개발용이며 공개 서비스에 적합한 보안이나 데이터 무결성을 보장하지 않는다.

최초 실행 시 `MAINTENANCE`, `ANNOUNCEMENT`, `MAINTENANCE_SCHEDULE` 환경 변수로 초기 공지와 점검 상태를 정할 수 있다. 이후 상태는 DB에 저장되며 `/admin`에서 변경한다. 기존 접속자를 자동 종료하지 않고 예정 시간은 안내 문구로만 쓰며 자동 실행되지 않는다. 운영용 보안 기능은 아직 완성되지 않았다. 채팅 명령 `/w 이름 내용`, `/block 이름`, `/unblock 이름`, `/report 이름 사유`를 사용할 수 있다. 차단과 신고는 DB에 저장된다. `ADMIN_TOKEN`으로 보호된 `GET /api/admin/reports`는 최근 신고를 반환하며 처리 화면과 결과 통보는 아직 없다.

신고 결과는 게임의 채팅 영역에서 `내 신고 확인`으로 볼 수 있다. 운영자는 `ADMIN_TOKEN`으로 `POST /api/admin/reports/resolve`에 JSON `{"id": 신고번호, "resolution": "처리 내용"}`을 보내 처리 결과를 기록할 수 있다. 운영자 인증과 개인정보 보호, 신고 처리 정책은 공개 서비스 전에 보강해야 한다. 클라이언트와 서버의 입장 프로토콜 버전이 다르면 접속을 거부하므로 변경 후 양쪽을 함께 재시작한다.

게임 채팅 패널의 고객 문의에서 문의를 접수하고 본인의 문의·답변 상태를 조회할 수 있다. 운영자는 `ADMIN_TOKEN`으로 보호된 `GET /api/admin/inquiries`와 `POST /api/admin/inquiries/respond`를 사용할 수 있다. 답변 요청은 JSON `{"id": 문의번호, "response": "답변 내용"}` 형식이다. 현재는 개발용 API이며 운영 계정별 권한·감사와 개인정보 처리 절차는 미완성이다.

게임 내 `나가기`는 저장 결과를 기다린 뒤 로그인 화면으로 돌아간다. 저장이 실패하면 다시 시도할 수 있다. 연결이 예기치 않게 끊긴 뒤 저장에 실패한 경우 서버가 실행 중인 동안 해당 상태를 보관하여 재접속 시 저장을 다시 시도한다. 창 강제 종료, 서버 종료·장애 및 운영 환경의 완전한 데이터 복구는 아직 보장하지 않는다.

게임 정보의 계정 관리에서 로그인한 계정의 비밀번호를 변경할 수 있다. 비밀번호 분실 복구는 아직 제공하지 않는다. 설정 영역에서 창 크기와 전체화면을 변경할 수 있으며 해당 기능은 Electron 클라이언트 전용이다. 서버를 공개하기 전에는 TLS와 인증 요청 제한 등 운영 보안이 필요하다.

시작 지점에 상인이 있으며 게임 정보의 상점에서 물약을 구매하고 나무·검·물약을 판매할 수 있다. 상인에게 가까이 있어야 하며, 구매·판매 전에 수량과 합계를 확인한다. 신규 캐릭터와 기존 데이터에 골드 항목이 없는 캐릭터의 초기 잔액은 20골드다.

게임 화면의 파티 패널에서 최대 4명의 파티를 만들 수 있다. 다른 플레이어를 클릭한 뒤 초대하고, 초대받은 플레이어는 30초 안에 수락하거나 거절한다. 파티 상태와 채팅, 리더 위임을 제공한다. 현재 파티는 메모리에만 유지된다. 예기치 않은 연결 종료는 60초간 재접속을 기다리고, 게임 내 나가기나 캐릭터 삭제 시 탈퇴한다. 서버 재시작 시 파티는 사라진다.

친구 패널에서 선택한 플레이어에게 친구 요청을 보내고 요청 수락·거절·삭제 및 접속 상태 공개 여부를 설정할 수 있다. 목록은 친구 접속과 공개 설정 변경 시 갱신되며 수동 새로고침도 가능하다. 파티 리더는 초대 허용을 켜거나 끌 수 있다. 친구 관련 테이블이 처음 생성되므로 서버를 재시작해야 한다.

개발 서버의 `/admin`에서 관리자 토큰을 입력해 서버 상태, 신고와 문의를 조회하고 처리할 수 있다. 이 화면은 로컬 개발용이며 운영 서비스에 필요한 인증·감사·TLS를 제공하지 않는다.

로그인 후 캐릭터 목록에서 기존 캐릭터 또는 새 생성 항목을 선택해 입장한다. 현재 계정당 캐릭터 하나만 지원한다. 새 캐릭터는 기본 색상·머리·표정을 선택할 수 있으며, 기존 캐릭터의 외형 변경은 아직 지원하지 않는다.

캐릭터 삭제는 게임 내 계정 관리에서 이름을 다시 입력해 요청한다. 삭제된 캐릭터는 계정에서 분리되어 게임에서 복구할 수 없지만, 이름과 신고·문의 등에 연결된 기록 및 기존 캐릭터 데이터는 데이터베이스에 보관된다. 같은 이름은 재사용할 수 없다. 계정 탈퇴나 개인정보 삭제 기능은 아직 구현되지 않았다.

시험 시련은 화면의 텍스트 기반 프로토타입으로, 1~4명이 60초 안에 5회 공격하는 공유 목표를 확인한다. 파티 리더가 시작하면 접속 중인 파티원은 각자 입장한다. 현재 보상과 별도 3D 던전 월드는 없으며, 시련 상태는 서버 메모리에만 유지된다.

개발용 데이터 보관: 로컬 PGlite의 `.data/postgres`는 서버를 완전히 종료한 뒤 별도 안전한 위치에 복사한다. 복구를 시험할 때도 서버를 종료하고 기존 데이터를 보존한 다음 별도의 격리 경로에서 사본을 확인한다. 실행 중 폴더 복사본의 일관성은 보장하지 않는다. 외부 PostgreSQL은 해당 서버에 맞는 백업·복구 도구와 접근 권한을 별도로 구성해야 한다. 현재 자동 백업, 시점 복구 및 정기 복구 검증은 구현되지 않았다.

개발용 `/admin`의 지표 버튼은 DB 연결 확인, 프로세스 시작 이후 쿼리·오류 수와 최근 오류 시각, 마지막 쿼리 소요 시간, 최근 약 1분의 이벤트 루프 지연 p95와 프로세스 메모리 사용량을 표시한다. DB 연결 확인 요청 자체도 쿼리 수에 포함된다. 서버 재시작 시 지표는 초기화되며, 장기 모니터링·알림을 대체하지 않는다.

개발용 운영 화면에서 신고 처리와 문의 답변의 최근 100건 이력을 조회할 수 있다. 처리와 이력은 같은 데이터베이스 작업에 기록된다. 현재 모든 작업은 공통 관리자 토큰으로만 표시되며, 개별 운영자 식별·권한 분리 및 변경 불가능한 감사 기록은 지원하지 않는다.

개발용 `/admin`에서 계정 아이디·사유·기간을 입력해 접속을 제한하거나 해제할 수 있다. 제한 기간은 1~720시간이며 적용 시 기존 연결을 종료하고 미사용 입장 토큰을 폐기한다. 조치는 공통 토큰 이력으로 기록된다. 실제 운영 전에 개별 운영자 권한, 동시 인증, 이의 제기와 보안 정책이 필요하다.

개발용 운영 화면에서 계정 제한·해제 시 관련 신고 번호를 선택적으로 입력할 수 있다. 해당 신고의 대상 캐릭터가 그 계정에 속한 경우에만 조치와 이력이 기록된다. 신고를 연결해도 신고가 자동으로 완료되지는 않는다.

로그인 화면의 계정 문의는 계정 제한 중에도 아이디와 비밀번호로 본인 확인 후 접수·조회할 수 있다. 운영자는 `/admin`의 계정 문의에서 답변한다. 비밀번호 분실 시의 별도 본인 확인·복구 기능은 없으며, 원격 공개 전 TLS와 운영 보안이 필요하다.
